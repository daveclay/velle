# Velle Evaluation Model (v0)

The operational semantics of a transpiled Velle system: what the runtime does, stated once, in execution order. Nothing here is newly decided — this consolidates semantics settled across the Reference ([§4](Reference-04-State-and-commits), [§8](Reference-08-Refinements), [§11](Reference-11-rule-when-on), [§13](Reference-13-Exit-triggers), [§16](Reference-16-Sweeps)–[§19](Reference-19-Self-referential-folds-and-tolerates), [§21](Reference-21-never)) so an implementer follows an algorithm instead of re-deriving one from rationale. The handful of genuinely new calls are **v0 spike choices** — execution decisions below the language, made for the runtime-testing spike, not semantics — marked `[S#]` and collected at the bottom.

The input/output surface (the acts' typed input values and the `commit` overloads over them, tick and clock functions, typed accessors, the query API) is the harness contract in [Reference §22](Reference-22-Open-unresolved)'s scope statement; this document is what happens *inside* a call.

## State

The state is the set of all shape instances and their stored fields ([Reference §4](Reference-04-State-and-commits)). Per instance, the runtime holds:

- **`id`** — opaque identity, fixed at creation, `==` only ([§5](Reference-05-Scalars)).
- **Stored fields** — scalar values, to-one references, and declared `many` collections (a many-to-many's edge set as a set of references; a `many <scalar>`'s set of values — [§6](Reference-06-Relationships), ownership). *Inferred* `many` sides are derived from the declared side and need no storage of their own; derived collections (`= (Shape where ...)`) are computed on read like any derived property.
- **Timestamp fields** — `on create` fixed at the creation commit; `on update` advanced by every commit that writes a stored field of the instance, creation included ([§5](Reference-05-Scalars)).
- **Captures** — per-membership memory: for each refinement membership currently held that declares captured properties, the values fixed at entry ([§8](Reference-08-Refinements); lifecycle below).

Derived properties are never stored — they are computed on read from current state ([§7](Reference-07-Derived-properties)). Refinement membership is never stored — it is the predicate, evaluated against current state ([§8](Reference-08-Refinements)). [`[S1]`](#v0-spike-choices) v0 state is in-memory only: no persistence, no crash recovery; the crash-window semantics the language defines (guards, backstops) remain exercisable because backstop ticks are explicit harness calls.

## Commits and transactions

A **commit** is one mutation entering state at a discrete moment: an act instance, one rule firing's effects, or a tick ([§4](Reference-04-State-and-commits)). A **transaction** is the all-or-nothing envelope: an act's commit plus every commit its consequences produce, except where a boundary intervenes ([§11](Reference-11-rule-when-on)). Boundaries arise three ways — declared (`after commit`), inherent (schedule sources), forced (external effects; none exist in v0 — no mechanism performs one, so `tolerates loss` parses and validates but marks nothing reachable).

### An exposed call

```
commitAct(actInstance):
  1. boundary validation: type-level checks first — a duplicate reference in a `many`
     field is refused here (collections are sets; multiplicity that matters is data on
     an edge shape, §6) — then the door: the prohibitions no rule can move (§21),
     evaluated over pre-state plus the act's closure as if landed and nothing
     processed — violation → refusal naming the act and what was violated;
     nothing begins
  2. begin transaction T
  3. C0 := apply the act commit — insert the instance with the committer's fields
     and, for an act declared `by`, the actor the binding handed in, under the
     name the clause binds (an act declares no `initially` or `timestamp`
     fields — V21; those clauses are evaluated at rule-created instances'
     creation commits, inside process)
  4. process(C0)                                   -- may recurse, growing T
  5. transaction-end `never` check over settled post-state, the door set skipped (§21)   [S5]
  6. any error in 3–5 → roll back T entirely; report the error to the caller;
     no automatic retry — re-invoking re-evaluates generators (§5)              [S4]
  7. make T durable (v0: the in-memory state simply stands)
  8. drain the after-commit queue accumulated in T: each entry runs as a fresh
     transaction by this same algorithm, synchronously, in queue order          [S2]
```

**Closure commits** (`act ... with`, [Reference §6 "Inline part creation"](Reference-06-Relationships#inline-part-creation-with)): C0 carries the container plus its declared inline parts as one commit — the entrants are the container and each part, so `process(C0)` matches rules per entrant, all inside T. The order the records are physically inserted in is a topological order over the closure's references — a value nested at a `one` field named in `with` before the record that points at it, a part after the record its back-reference points at, a record pointing at a sibling new value after that sibling — compilation's business, never observable: pre-state and post-state are defined at C0 as one moment, and no state where the container exists without its parts, or a batch without its nested origin, is ever observable. Back-references on parts are language-populated at insert; a reference to a sibling new value is resolved by the generated boundary, by the identity of the value in the input, before the runtime is entered ([Binding API](Binding-API)). Step 1's boundary validation extends to the parts — duplicate *references* are refused per collection, while inline part values are a bag (two identical values mint two distinct instances, each with its own `id`), and the refusal and constraint guardrails compile to this expose site over the whole closure.

**The door's moment** (ruled 2026-10-09, re-ruled 2026-10-14). The transaction end is the meaning: a prohibition constrains the settled transaction, and its rejection names the act in flight. The door is where the end check can be done early with the same verdict. A refusal or constraint ([Reference §21](Reference-21-never)) whose predicate reads nothing any rule writes, creates, or deletes cannot change its verdict by the rules running, so it is evaluated once, over the state as it would stand with the act's closure inserted and nothing else done — pre-state plus the act, before `process(C0)` — and skipped at step 5; every other prohibition is evaluated at step 5 only. Nothing is evaluated twice. Three things follow. The spelling is one spelling: `never (AssayReading where count(assay.assayReadings where hoursElapsed == this.hoursElapsed) > 1)` counts the arriving reading among its siblings at the door exactly as it would at transaction end, so the author writes the prohibition once and it means the same thing at either moment. The rules never see a forbidden state: a rule whose condition reads the series through `latest(... by hoursElapsed)` is well-defined only because the prohibition holds, and it runs only after the prohibition has been confirmed for the arriving act, so a duplicate hour mark is the refusal the author wrote ("AssayReading refused: this AssayReading would be an AssayReading where count(…) > 1") and not a selector's tie error from inside a rule. And a prohibition that reads what the request's handling moves — `never (FillPrescription where fillNumber != prescription.fillsRecorded + 1)`, where the handling records the fill and grows the count — is answered after the handling: evaluated at step 5 over the settled transaction, and refusing the request there. A tie inside a `never`'s own predicate remains an error at either moment, because that predicate's meaning is undefined at the tie ([Reference §10](Reference-10-Predicate-expressions)). The deleting commit (below) never runs the door: a deletion happens only inside a rule firing, mid-transaction and with siblings, and a check there would make sibling order observable [\[S3\]](#v0-spike-choices). Implementation latitude: running the door inside the runtime's own transaction immediately after C0's insert, with the act recorded on the transaction so the rejection names it, is observably the same as running it before the transaction, since nothing has been processed and a refusal reaches the engineer's store as nothing at all.

**The actor** ([Reference §22](Reference-22-Open-unresolved), "The actor"). An act declared `by` is committed with its actor: the binding passes the record it resolved the authenticated identity to, and step 1 refuses a missing one, or one outside the clause's base shape, as a type-level failure before anything begins; one outside the refinement the clause names is the desugared requirement's refusal at the door, carrying the actor's record among the records read through. The actor lands on the act's instance at C0 as a language-populated field, so every prohibition, refinement, and rule over the act reads it as it reads any member, and a durable act carries it to the store with its fields and back on hydration. The transaction T records the actor as well: a rule declared `by` ([V31](checks#v31--a-rules-actor-typed-by-reachability)) fires with the bound name resolving to that record, or to absence when T began at a tick, an `after commit` firing, or an act without `by`. A tick's transaction has no actor, and an `after commit` firing's has none, whichever commit it follows — what the backstop cannot see, the prompt firing may not use. **A read for a viewer** ([Reference §8](Reference-08-Refinements), "Who may see a record") applies the shape's visibility clauses and nothing else does: a query carrying a viewer admits the records whose clauses admit that viewer — a clause naming a shape the viewer's record belongs to, a refinement the viewer is a member of, a predicate over the record with the viewer bound that holds, or `anyone` — after the pre-filter's superset and the predicate, in memory; a fetch of a record no clause admits resolves absent, as a deleted one does; a model object is projected with the fields whose clauses admit no viewer absent. A query with no viewer is the engineer's own view of their store and is never filtered. Evaluation consults none of this: a rule, a derivation, and a prohibition read every member whoever is asking, and a refusal is projected for the actor only as it is handed back ("Errors, refusals, and retry"). A record that must exist before any act can be committed — the first administrator where hiring is gated on one — is **seeded** outside the trust boundary (`VelleSystem.seed`): the in-memory form of a row a migration or the engineer's own code wrote to the store, inserted with no door, no rule, and no prohibition, written through the commit callback when a store is connected.

Worked example, one plate with readings at hours 0, 24, and 48, running peaks 10, 80, 80. A second reading at hour 24 arrives. At the boundary the reading is counted among its siblings: two at hour 24, the predicate is true, the act is refused by name, and no rule runs. Without the boundary check the same act would reach the rules first; the plate's peak reads the hour-48 reading's predecessor, `latest(AssayReading where assay == this.assay and hoursElapsed < 48 by hoursElapsed)`, two readings tie at hour 24, and the caller receives a runtime error that names a datum and says the model is underspecified, when the model had already ruled the state out. Whether the caller saw the error or the refusal would then depend on whether any rule in the spec happens to read the series.

### Processing one commit

```
process(C):
  1. delta: the fields C wrote and the instance C inserted — statically known
     per commit kind (literal assignment paths, §12; act shape; tick datum)
  2. membership flips: for every refinement whose predicate reads the delta
     (the derived trigger sets, §11 "Rules ground in commits"), evaluate
     pre-state vs post-state membership for affected instances:
       entrants — false before C, true after
       leavers  — true before C, false after
  3. captures: for each entrant into a capture-declaring refinement, evaluate
     its captured expressions against post-state now, and store them; for each
     leaver, mark its captures for retraction at the close of C — exit rules
     fired from C may still read them (§13, last-reader)
  4. freeze enforcement is not a runtime step: writes to frozen fields were
     proven impossible statically (§8) — v0 asserts and hard-errors if violated
  5. firings := for every rule whose trigger set includes C:
       `when R`          — one firing per entrant into R
       `when leaving R`  — one firing per leaver from R
     partition by preposition:
       on commit    → fire now, inside this transaction (step 6)
       after commit → append (rule, subject) to the transaction's after-commit queue
  6. for each in-transaction firing, in any order [S3]: apply its body as a new
     commit C' — all statements land together, `then` ordering respected within
     the body (§15), a `for each` block's statements landing once per element
     (§14) — and recurse: process(C')
  7. close C: retract the captures marked in step 3
```

Recursion terminates because the validator proved quiescence — the condition graph is a DAG or its cycles are broken by disarming guards ([checks catalog](checks), [V16](checks#v16--quiescence-coarse)); v0 additionally enforces a cascade-depth backstop that errors the transaction if exceeded [`[S3]`](#v0-spike-choices).

Ordering within step 6 is **never observable in a valid spec**: the validator rejected any pair of sibling firings that could conflict ([V1](checks#v1--one-writer-disjointness), [V15](checks#v15--confluence-coarse)). The claim is audited and executable — every example world is rebuilt under a reversed firing order on every build and must fingerprint identically (`compiler/src/test/kotlin/velle/CommutationSweepTest.kt`, `SiblingConfluenceAuditTest.kt`). Where one firing's commit satisfies another rule's condition, ordering is causality — the recursion structure provides it.

### Transient acts (`transient act`)

A `transient act` is an **input to the state, not a member of it** ([Reference §4, "Transient acts"](Reference-04-State-and-commits#transient-acts-transient-act)): its instance exists only within its own commit's transaction. The exposed-call algorithm changes in two places. Step 7 additionally **removes the act instance from the state** (it never becomes durable; only its consequences do). And in step 5's firing selection, **the act's partitions are decided exactly once, at C0**: consequence commits within the transaction never re-partition it — without this, an act whose own effects flip the partitioning state would drift into the other side mid-transaction (apply a withdrawal, go overdrawn, and be refused *by the same request*). Everything else is unchanged: the instance is fully present while its transaction runs, so its refinements evaluate normally at C0, its handling rules fire and read its fields, and the transaction-end `never` check sees a consistent world. By the time the after-commit queue drains (step 8), the act is gone — which is consistent, because the validator bans `after commit` and schedule triggers on transient-act conditions ([checks catalog](checks), [V17](checks#v17--transient-isolation)): nothing that runs after the transaction may depend on the act.

Rollback needs no special case — an error rolls back the whole transaction, act included, exactly as for ordinary acts. `CommitResult.Accepted.id` remains an opaque receipt; the id names an instance that no longer exists, and since `id` supports only `==`, nothing can be asked of it.

### Entry and exit are commit-local

"Newly-satisfying" is always relative to one commit's pre/post states ([§11](Reference-11-rule-when-on)) — the runtime never stores membership, never diffs history, and never needs to: both states are transiently available while processing C, and that is the only place transitions exist (the transition law, [§11](Reference-11-rule-when-on)). September's re-entry is a new entering commit and fires entry rules again — episodes are free at commit granularity ([§11](Reference-11-rule-when-on)); durability across boundaries is the guard apparatus's job, visible in the spec ([§18](Reference-18-Run-once-guards)).

**The deleting commit.** A `delete` ([Reference §12, "Deletion"](Reference-12-Assignment#deletion-delete)) makes its target transient at that commit, the mirror of a transient act: the instance is fully present in the pre-state, every rule the commit fires reads it as one of its last readers, and step 7 removes it. It leaves every refinement it was a member of at once — by deletion, not by a predicate flipping, and those are different exit causes ([Reference §13, "Deletion as a second exit cause"](Reference-13-Exit-triggers#deletion-as-a-second-exit-cause-when-deleted)): for each state R it was in, `when deleted R` and `when leaving or deleted R` rules fire from this commit, while bare `when leaving R` and `when leaving not deleted R` rules do not. Nothing after the transaction's close may read the instance, which is why the deletion-side forms are transaction-bound ([V28](checks#v28--deletion-stranding)).

### `after commit`

An `after commit` firing runs as its **own transaction**, begun only after the triggering transaction is durable ([§11](Reference-11-rule-when-on)). The act stands even if the firing fails; the declared backstop schedule heals the gap — which in v0 means: the harness calls the backstop tick function, and the guard makes re-evaluation harmless ([§18](Reference-18-Run-once-guards)). [`[S2]`](#v0-spike-choices) v0 drains the queue synchronously, immediately after durability, in FIFO order — an execution choice invisible to a valid spec, since each entry is an independent transaction whose rule carries its own guard.

### Ticks

`tick(S)` is a commit whose changed datum is `today`/`now` — the clock the harness controls ([Reference §5](Reference-05-Scalars), [§22](Reference-22-Open-unresolved)). It does not advance the clock; clock movement is a separate harness call. Processing a tick:

- **Rules naming `S` with an entry-form condition** (`when R ... on S`): one firing per **current member** of R — re-checking, not transition-watching ([§11](Reference-11-rule-when-on)). Guards in the condition make the sweep idempotent and self-healing ([§16](Reference-16-Sweeps), [§18](Reference-18-Run-once-guards)). Each firing is its **own transaction** ([§17](Reference-17-Schedule-triggers)): one record's failure rolls back only itself; the rest stand and disarm their guards; the next tick retries exactly the stragglers. A firing that a `never` rejects (a constraint, [Reference §21](Reference-21-never)) has no caller to return the refusal to, and its guard never disarms, so the validator refuses the spec where it can see the case: a scheduled or after-commit rule creating a record the constraint consults ([`checks.md`](checks) [V29](checks#v29--a-firing-with-no-caller-joins-never-induction-coarse), the [V10](checks#v10--never-obligations-and-spend-tracking) posture). A constraint that reads the clock is refused too ([`checks.md`](checks) [V30](checks#v30--a-constraint-that-reads-the-clock-coarse)): the clock is a writer with no caller, and the books could age into the forbidden state with no act to refuse. What validation never saw — a record that arrived through a legacy mapping and aged into a constraint, met by a firing on that state — is rejected here: once the sweep is done the tick **throws** `TickRejected` (`compiler/src/main/kotlin/velle/Rejection.kt`), carrying the schedule, the moment, and one rejection per rejected firing — the same data an act's refusal carries (below, "Errors, refusals, and retry"), with the rule and the record it ran for in place of the act. The harness owns what to do with it; the condition stands until a person changes the books, so the next tick throws again.
- **Rules naming `S` with `when leaving R`**: re-checking is impossible for exits (a non-member carries no trace), so the subjects are the **leavers at the tick commit itself** — instances whose membership flips false because the tick's datum changed (aging out) — the same commit-local detection as any commit, the tick being the commit ([§17](Reference-17-Schedule-triggers), "transient membership is a policy"). *Accepted for v0, but derived here rather than stated anywhere in the Reference — flagged for stress-testing against realistic specs (`working-docs/QUESTIONS.md`, OQ16): in particular, exits caused by non-tick commits between ticks are observed by `on commit` leaving-rules only, so a leaving-rule that names only a schedule sees only aging-out exits — confirm that reading survives real use cases.*
- **Rules not naming `S`** are untouched: a tick serves exactly the rules that list it in `on`. This is why `when OverdueInvoice` with no schedule under-fires (never observes entry by aging) and the validator says so ([V3](checks#v3--unfireable-rule)).

## The universal transaction

Where state lives beyond the process — the hydrating runtime over engineer-owned storage — the runtime reads through engineer-supplied resolvers and lands each transaction's mutation set through a commit callback. The **universal transaction** is the contract those two surfaces must jointly honor, per envelope. It is stated here because it is semantics — what "transaction" *means* once the store is real — and it is the one part of this document addressed to the *store* implementer rather than the runtime implementer: each clause states the guarantee in one sentence, then says what it means in practice. v0's in-memory state [`[S1]`](#v0-spike-choices) satisfies every clause trivially (one process, one thread, no store). No clause is validator-checkable — these are the premises the checks' theorems rest on, not checks themselves ([`checks.md`](checks) gains nothing).

Velle never verifies these guarantees at runtime — it cannot; they concern behavior across processes and stores it never sees. That is what makes the contract worth reading carefully: **a broken clause fails nothing visibly.** The spec still validates, the tests still pass — but the things the validator proved (no double-applied deposits, prohibitions that hold, rules firing exactly when they should) quietly stop being true. How you deliver the guarantees is entirely yours: **one `SERIALIZABLE` database transaction per envelope delivers all five trivially**, and that should be the default choice until measurement says otherwise. An envelope that spans multiple databases, API calls, or files is distributed-transaction territory, and Velle stays out of it — coherence there is your engineering. The clauses below are the definition of coherent.

**U1 — Snapshot.**
*The guarantee: every resolver read within one envelope is answered from a single consistent state — the settled end-state of the transaction serialized immediately before this one ([U3](#the-universal-transaction)).*

In practice: while Velle processes one commit, every question it asks your store must be answered *from the same frozen moment*. If it asks two questions and someone else's transaction lands between your two answers, each answer was true at *some* moment — just not the same one, and that is a breach even though neither answer was individually wrong. The straightforward implementation: open one database transaction with consistent-read isolation when the envelope begins, and answer every resolver call from it. The runtime meets you halfway — it never asks the same question twice in one envelope (fetches are memoized), and it reads the envelope's own in-progress writes from memory — so you never serve mid-envelope state, and must not. A tick is the same deal: each tick opens a fresh look at settled state.

**U2 — Atomicity.**
*The guarantee: the envelope's mutation set becomes durable as one unit, or not at all.*

In practice: at the close of the envelope, your commit callback receives everything the transaction did as one payload — the act's insert, every rule-produced insert and update, and the capture writes and deletes. Write all of it or none of it. If anything goes wrong — your database throws, a constraint fires, a connection dies — the whole envelope must disappear and the error propagate; the callback runs *inside* the envelope, so throwing from it *is* the rollback signal, and the caller gets the error. No later envelope may ever observe half a payload. With one database this is just `BEGIN … COMMIT`/`ROLLBACK`; with storage spanning systems, making failure leave no visible half-state is your job. One thing you never see: refused acts — boundary validation runs before the envelope exists, so a refusal reaches your store as nothing at all.

**U3 — Serialization.**
*The guarantee: the observable history is equivalent to some order in which transactions ran one at a time, each reading ([U1](#the-universal-transaction)) its predecessor's settled end-state — with real time respected between conflicting transactions.*

In practice: "as if one at a time" does **not** mean single-threaded. Two envelopes that touch entirely different data may run fully in parallel — no observer can tell, and the contract doesn't care. The obligation is only between envelopes that touch the *same* data: those must take turns, and the one acknowledged first goes first (that is all "last-in-wins" ever meant). The subtle part: "touching the same data" includes *checks*, not just writes. Velle's guard idiom reads "no `DepositApplication` exists for this deposit yet," then creates one. Run two envelopes for the same account concurrently under plain snapshot isolation and *both* see "none exists yet" — both fire, and the deposit applies twice. That failure mode (write skew) is exactly what popular defaults like Postgres `REPEATABLE READ` permit, so **snapshot isolation is not sufficient**. Two honest implementations: `SERIALIZABLE` isolation on one database, which buys the whole clause outright; or a lock on the entity the envelope revolves around — `SELECT … FOR UPDATE` on the account row, a per-account mutex, a partition key — so same-account envelopes serialize and different accounts run in parallel.

Knowing *what value to lock on* is answered from the spec itself (OQ40, settled 2026-08-18). The compiler derives, per act and per schedule-fired rule firing, a **serialization domain**: the set of **queue keys** the envelope's work revolves around, computed from the envelope's whole read-and-write footprint — predicate reads included, which is what catches the guard example above (the guard read and the witness creation meet on the same key). Two envelopes conflict iff their domains intersect: path keys by the row they evaluate to (`deposit.account`), value keys by equal committed values (the uniqueness case, where no row exists yet to lock), and a whole-shape width with anything touching that shape. The domain is derived, never declared — no author writes a queue key — and it reaches the engineer as the generated commit function's contract ("Queue key: [deposit.account]") and reaches both engineer and product owner as the contention map ([`diagrams.md`](diagrams)). Where a read correlates to no key the domain honestly widens to the whole shape and the [A5](checks#a5--contention-width) advisory ([`checks.md`](checks)) demands a stated policy: correlate the read, move the rule to a schedule, or declare `tolerates contention` on the declaration carrying the read. Delivering the serialization across stores remains the engineer's mechanism choice, per the exclusions below; the contract's job is to *name* the keys. What the mechanism owes the contract is one moment: each key's concrete value is computed *at admission*, before the envelope's work runs, against pre-commit state plus the act's own inputs — and "pre-commit state" includes **captured members**, which are committed state recorded at membership entry (typically real columns), so a key may hop through one (`reopenTicket.ticket.closedBy`) and the store must keep captures readable at admission time (ruled 2026-08-19; OQ42 audit R1).

**U4 — Permanence.**
*The guarantee: once an envelope is reported accepted, its effects are durable — every later snapshot reflects them.*

In practice: "accepted" must mean *it is in the store the next read hits, and it stays there*. Velle's entire recovery story is built on data: a `DepositApplication` row is the only memory that a deposit was applied. If that row vanishes — a cache that evicts, an acknowledgment sent before the write is actually durable, a restore from a stale backup — the hourly backstop sweep sees an unapplied deposit and applies it again. The same holds across processes: a second runtime hydrating your store must find everything the first one committed, because guard rows, episode flags, and capture rows are how it knows what already happened. This clause is also what `after commit` rules stand on — their firing begins only after the triggering transaction is durable, so they always see its effects.

**U5 — No side doors.**
*The guarantee: between one transaction's end and the next one's snapshot, Velle-visible state does not change — every mutation to the data behind the resolvers enters as a commit through the generated surface.*

In practice: **reading is always safe** — query the tables backing Velle shapes with your own SQL as much as you like; reads commit nothing ([§4](Reference-04-State-and-commits)). Writing is the door that must stay shut: a hand-run `UPDATE`, a migration script, an admin console, another service writing the same tables — each changes data with no rules fired, no prohibitions checked, no guards observing. Everything Velle proved assumed changes arrive as commits; a side-door write is a case none of that analysis considered, and nothing will flag it — the data is simply wrong in ways the spec promised were impossible. Your own tables *beside* the Velle-backed ones are none of the contract's business. When outside data must flow in, it enters as commits through the exposed surface, or through a mapping that carries its validation obligation ([§21](Reference-21-never)).

**A read is a read-only snapshot.** A query through the read API ([Reference §22](Reference-22-Open-unresolved), the generated typed surface and whatever the engineer builds over its generic read entry) is a transaction of one clause: it is answered from a single consistent state, the settled end-state of some completed envelope ([U1](#the-universal-transaction)), and nothing else of the contract applies to it. It commits nothing ([U2](#the-universal-transaction) and [U4](#the-universal-transaction) have nothing to make durable), it takes no queue key and waits for no envelope ([U3](#the-universal-transaction) orders only transactions that write), and it is the "reading is always safe" of [U5](#the-universal-transaction) seen from inside the generated surface. In practice: open a read-only snapshot transaction, answer every resolver read the query makes from it, close it. The isolation a read gets is exactly this snapshot; finer choices are not offered yet.

### What each clause carries

The language-side layer, for the reader who works on Velle rather than against it: every static analysis that makes a validated spec trustworthy is a theorem with these clauses as premises. The map from clause to the proofs that spend it — what specifically stops being true when a clause is violated:

| clause | spent by |
|---|---|
| [U1](#the-universal-transaction) Snapshot | sibling-commutation/confluence analyses (all of a commit's firings read one state); relevance gating; the transaction-end `never` check (a settled world to check) |
| [U2](#the-universal-transaction) Atomicity | disarm soundness (mutation and witness are statements of one body — one payload); the capture last-reader contract (capture read and retraction land in one envelope); fan-out atomicity ([§20](Reference-20-State-change-patterns), all-or-nothing batches) |
| [U3](#the-universal-transaction) Serialization | one-writer at transaction scope; last-in-wins as the cross-commit order; guard soundness under concurrency (no two envelopes both see the guard armed) |
| [U4](#the-universal-transaction) Permanence | `after commit` + backstop healing; intent-before-effect (the intent durably precedes the effect's envelope); cross-process guards and episodes |
| [U5](#the-universal-transaction) No side doors | relevance gating; inductive `never` proofs; every derived trigger set (a side-door write fires no rules — drift stops being commit-mediated) |

### What the contract deliberately excludes

- **Mechanism.** One DB transaction, sagas over three stores, a file plus an API — Velle never knows. The contract is the *what*; the *how* is the engineer's, permanently ([Reference §22](Reference-22-Open-unresolved), "External input").
- **The world/state gap.** No clause makes an external effect atomic with its record — nothing can ([§11](Reference-11-rule-when-on), "the gap between the world and the state is irreducible"). The contract governs state; the gap is answered above the contract by intent-before-effect, `after commit`, and `tolerates loss`.
- **The pre-filter.** `fetchCandidates` over-returning is always legal — a performance surface under the superset contract (`compiler/src/main/kotlin/velle/Hydration.kt`, `fetchCandidates`), orthogonal to correctness. Only `fetchCaptures` sits on the correctness side of that line ([§7](Reference-07-Derived-properties)'s deliberate asymmetry there), and its guarantees are [U2](#the-universal-transaction)/[U4](#the-universal-transaction)'s.
- **Refusal handling.** Wrapper code may log, rate-limit, or audit refused acts in the engineer's own tables — that data is theirs, not Velle-visible state, and [U5](#the-universal-transaction) doesn't touch it.

### Handles and their lifetime

Inside the runtime a record is a number, the handle, minted when the runtime creates the record or first loads its row. A handle is private to one running system. The identity that crosses the boundary is the pair of shape and store key that every reference carries ([Binding API](Binding-API), "Reading a record"), and the runtime keeps a map between the two.

Over a store that map lives for one unit of work: a commit together with the `after commit` firings it queues, a tick, or one read. The generated commit converts the input's references to handles, calls the runtime, and when the call returns the runtime drops the map and the rows it loaded. The generated read surface does the same around each read. Memory is therefore bounded by the largest single unit of work, not by how many records the system has ever touched. In memory, with no store, the handle is the identity and nothing is dropped.

A record the refused transaction created never reached the store and has no key. A rejection names such a record by its handle, which is only meaningful for reading the message.

## Capture lifecycle

One timeline per membership ([§8](Reference-08-Refinements), [§13](Reference-13-Exit-triggers)): **entry commit** — captured expressions evaluated against post-state, values fixed; **during membership** — readable wherever the refinement's properties are in scope (narrowing, [§8](Reference-08-Refinements)); **exit commit** — exit rules fired from that commit may read them (the last reader); **close of exit commit** — retracted. Re-entry re-captures from scratch. A capture never survives its transaction — which is why a capture-reading exit rule can never be `after commit` (validated, [V7](checks#v7--capture-transaction-boundedness)); durable reactions read reified acts instead ([§13](Reference-13-Exit-triggers)). Deletion is the exit commit for every membership the instance held, at once: the deletion-side rules are the last readers of all of its captures, and all retract at that commit's close ([§13, "Deletion as a second exit cause"](Reference-13-Exit-triggers#deletion-as-a-second-exit-cause-when-deleted)).

## Errors, refusals, and retry

Three distinct outcomes of an exposed call, never conflated:

- **Refusal** (step 1, or step 5 for a prohibition the request's handling moves): the act violates a type or a `never` (a refusal or a constraint, [Reference §21](Reference-21-never)) — named in the result; the transaction, if one began, is rolled back whole and nothing commits. Refusal is whole: the unit refused is the closure the commit would have been ([§4](Reference-04-State-and-commits)), never a part of it — a request that should succeed in part is separate acts, or rejection-as-data, below. A prohibition's refusal carries its context as data (`compiler/src/main/kotlin/velle/Rejection.kt`): the declaration as the author wrote it, so a requirement renders as the requirement unmet and a `never` as the forbidden configuration reached; the act with its fields; the records the transaction produced beyond the act; the records that would have been in the forbidden state; the records the act references that the prohibition read through, which is what the person was acting on; any other record it read; and the evaluation step by step, every member read and refinement test. The result's `reason` is the default rendering of that data, so a readable message needs no binding code, and the binding code builds a more specific one from the data when it wants to. A tick's rejection is the same data, thrown rather than returned ("Ticks" above), with the rule and its subject in place of the act; an after-commit firing's rejection is the same data recorded on the system (`afterCommitRejections`, `compiler/src/main/kotlin/velle/Runtime.kt`), since the act already stood and nobody was asking. Both are reachable only through the runtime backstop, [V29](checks#v29--a-firing-with-no-caller-joins-never-induction-coarse) and [V30](checks#v30--a-constraint-that-reads-the-clock-coarse) refusing the cases the spec shows.
- **Rejection-as-data**: not an error at all — the act commits, the refusing fact lands, the caller reads it back (the pattern in [`patterns.md`, "Validation rejection is data"](patterns#validation-rejection-is-data)). The runtime does nothing special.
- **Transaction error** (step 6): an unexpected failure mid-transaction — the whole envelope rolls back, the caller is told, and retry is the caller's re-invocation [`[S4]`](#v0-spike-choices), which re-evaluates generators ([§5](Reference-05-Scalars)).

## v0 spike choices

Execution decisions for the spike — below the language, revisable without touching semantics:

- **[S1] In-memory state.** No persistence, no crash recovery. Backstop/guard semantics stay exercisable via explicit backstop ticks.
- **[S2] Synchronous `after commit`.** The queue drains immediately after the triggering transaction, FIFO, on the calling thread. Unobservable to a valid spec (independent guarded transactions).
- **[S3] Deterministic iteration + depth backstop.** Sibling firings run in declaration order (any order is valid — [V16](checks#v16--quiescence-coarse) proved commutativity); a cascade-depth limit errors the transaction as a belt-and-suspenders backstop behind the static quiescence proof.
- **[S4] No automatic retry.** A failed transaction reports; retrying is the caller calling again. (A real runtime might retry internally; the semantics — generators re-evaluated, same commits re-produced — don't change.)
- **[S5] Runtime `never` check at transaction end.** Guarantees ([Reference §21](Reference-21-never)) are statically proven, so a runtime violation is an internal error (a bug in the proof or the runtime) — v0 checks anyway because in-memory checking is cheap and the spike exists to find exactly such bugs.
