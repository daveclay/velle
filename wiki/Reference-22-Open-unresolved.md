# 22. Open / unresolved

**Current milestone — the v0 validator/transpiler (scope settled).** v0 implements [§3](Reference-03-shape)–[§21](Reference-21-never) as written — plus two constructs adopted after the original scope statement (`transient act`, [§4 "Transient acts"](Reference-04-State-and-commits#transient-acts-transient-act), from the transient-acts investigation; the act's closure `act ... with`, [§6 "Inline part creation"](Reference-06-Relationships#inline-part-creation-with); deletion and its trigger family, [§12 "Deletion"](Reference-12-Assignment#deletion-delete) and [§13 "Deletion as a second exit cause"](Reference-13-Exit-triggers#deletion-as-a-second-exit-cause-when-deleted), from the delete investigation) — validated and transpiled to an executable runtime driven through a test-harness boundary, itself fully settled. Input enters through the `act` construct: each `act` declaration transpiles to a typed input value — a Kotlin data class of the act's stored fields, `NewSubmitPayment` for `act SubmitPayment` — and a `commit` overload that takes it: the thing the engineer's own transport code calls to submit a mutation, and a class any transport can bind a request to by reflection with nothing written by hand — plus a generated `main`-style entry point for driving the system manually. The declaration names no mechanism; transport, persistence, and serialization are the engineer's code, outside the spec (the external-input item below). A call returns acceptance or a refusal, each carrying the input value it was handed, so a refusal holds what was refused as the engineer's own type and never as a map; a refusal names what was violated — the type-level failure or the specific `never`, the latter carrying its context as data ([§21](Reference-21-never)) — and on refusal nothing commits. Refusal is whole: the unit accepted or refused is the closure the commit would have been ([§4](Reference-04-State-and-commits)), never a part of it, so a request that should succeed in part is submitted as separate acts, or lands whole with its refused subset an ordinary refinement the rules answer ([§2](Reference-02-Philosophy), the errors-are-refinements pattern; [§4](Reference-04-State-and-commits) "Every request gets a response"). Ticks enter the same way — each schedule name transpiles to a tick function the harness calls, since scheduled events and user acts are both external input ([§4](Reference-04-State-and-commits), [§17](Reference-17-Schedule-triggers)) — so schedule definition is not needed; when that construct lands, it defines *when* the tick functions are called, never what they do. Reading is **a query API the caller composes, over model objects**: every shape and refinement has a generated data class, the model object, every field read once at the moment of the read; a model object is itself a reference to its record (`Ref<Invoice>`, one type for both sides of the store boundary — a store row carries the same thing for each to-one field), so it passes wherever a reference is taken, equal to any other reference to the same record — equality is identity, and comparing fields is how an engineer asks whether two reads differ; a reference field holds a `Ref<T>` and `read(ref)` resolves it; and a query over any shape or refinement is composed by the caller from the spec's declared vocabulary (properties, references and inverses, refinement membership, the predicate language of [§10](Reference-10-Predicate-expressions), a required order over orderable datums, a page), returning model objects. A store key fetches one instance by identity the same way. Nothing is read *through* a reference: a view with getters would be a second, live read path beside the snapshot, and there is one. The spec declares definitions, never a query: a question a screen asks is written by whoever asks it, checked against the spec, and is not a line in the spec (OQ51, 2026-10-12). Querying is "read" in [§4](Reference-04-State-and-commits)'s sense and commits nothing. Built: the read protocol and its engine (`compiler/src/main/kotlin/velle/Read.kt` — a query as a value, checked by the validator's own predicate rules, answered from a read-only snapshot, ordered with the store key as the hidden tie-break, paged by cursor, counted and summed), the generic entry beside `commit` on the runtime, and per spec the typed Kotlin builder (`read.invoices.where { balance gt 0 }.orderBy { due.ascending }.page(20).fetch()`, `read(inv.customer)`, `read.invoice(key)`), one model object per shape and refinement (a static union is an interface its operands implement; a membership flag per refinement over the same base), and a registry for queries the engineer names (`examples/billing/output/src/test/kotlin/velle/QueryApiTest.kt`). Deferred past v0, with their items below: Mapping, schedule definition, the `act` construct's remaining details, the state partition declaration, extensible data types, and `why`/provenance — plus `visible to ... where`, removed from [§10](Reference-10-Predicate-expressions) until re-derived and synced. Nothing cut is exercised by any current example, and each re-enters post-v0 through its own item. The whole-language grammar is settled and normative in [`grammar.md`](grammar) — value expressions included, closing the formalization gap `## Predicate expressions` once left open for derived-property formulas. The operational semantics and the validator's [check catalog](checks) are settled and normative in [`evaluation.md`](evaluation) and [`checks.md`](checks) — the evaluation model an implementer follows (with its five signed v0 spike choices, the transient-act removal semantics, and the universal-transaction contract [U1](evaluation#the-universal-transaction)–[U5](evaluation#the-universal-transaction) the engineer's store must honor) and the [check catalog](checks) the validator runs, the coarse fail-closed slices of the open calibration questions included. [§6 "Inline part creation"](Reference-06-Relationships#inline-part-creation-with)) — a body is one commit, consequences share the act's transaction by default, `after commit` declares a boundary, and the irreducible world/state gap at an external effect is answered by the intent-before-effect pattern ([§4](Reference-04-State-and-commits), `## rule` "Transactions and `after commit`"); - **External input (`act`)** — resolves OQ5, "marking a shape as external input." Velle implements no transport: REST APIs, GraphQL, socket connections to a message bus are traditional-code territory it doesn't compete in; what it owns is the contract between the spec and the shape of the transpiled code. The construct names no mechanism (it originally carried a `using <Mechanism>` clause over transpilation plugins, dropped when the runtime model settled): transpilation generates one typed input value and one `commit` overload per act — the thing the engineer's own transport code calls to submit a mutation — and mapping any transport onto those input values is the engineer's code, permanently, not a deferred plugin design. An act is declared in exactly one place, where its fields are (`act CorrectEmail { ... }`): the keyword is the shape declaration plus the boundary, not the act-level sugar [§12](Reference-12-Assignment) rejects — nothing is hidden and no positional invariant is spent — and there is no second statement that opens a `shape` declared elsewhere (OQ50, settled 2026-10-12). An act is externally committable; a `shape` enters state only as a rule's effect. The set of `act` declarations *is* the trust boundary: the `never` guardrails for refusals and constraints ([§21](Reference-21-never)) compile to the generated surface at each act's boundary, and reachability sharpens — a `shape` with no producing rule is uncommittable, so a rule triggered by it is the unfireable-rule error ([§11](Reference-11-rule-when-on)). Authenticating the caller, finding their record, rate limits, quotas, and which machine clients may call which endpoint live in the engineer's wrapper code before the commit call, outside the language; who may commit an act, and who may see a record, is the spec's, through the actor ("The actor," below; OQ33, settled 2026-10-15). Which fields the committer supplies is read off the declaration forms — there is no field policy to state (resolves OQ31); a closure declaration (`act ... with`, [§6 "Inline part creation"](Reference-06-Relationships#inline-part-creation-with)) extends the same reading to inline parts, each a nested input value carrying every stored field minus the language-populated back-reference, to a `one` field named in `with`, whose reference the committer may supply by value, and to a field typed by a shape arriving elsewhere in the act, whose reference may name that new value ([§6](Reference-06-Relationships); the generated Kotlin is described on the [Binding API](Binding-API) page; OQ63, settled 2026-10-21). The generated input value carries every stored field of the act: the committer supplies them all, an optional (`?`) field by explicitly supplying the absence, and a convenience default belongs in the engineer's wrapper before the commit call, with the transport mapping it already owns. Derived properties are legal on an act and are never fields of the input — nothing is stored, so there is nothing to supply, and the `= expression` form states in the language that the value is calculated (on a transient act, whose one evaluation moment is its own commit, a derived property is also how an arrival-time value is fixed). `initially` and `timestamp` declarations on an act are compile errors ([`checks.md`](checks) [V21](checks#v21--act-field-forms)): a system-maintained value is no part of an external submission, so it lives on a `shape` — supplied by a materializing rule's `from` block, minted by `initially` at that record's creation commit, or populated as `timestamp` commit metadata — with the transient-act materialization ([§4](Reference-04-State-and-commits)) as the served spelling for a request whose durable record carries such fields. Still deferred as details of the construct, not open language questions: supplied-vs-generated `id` at a trust/legacy boundary (a legacy table's primary key, an upstream system's reference — mapping-side mechanics ride with the Mapping item, above). `act` is strictly input (OQ51, 2026-10-12): reading never goes through an act.
- **The actor** (`by`) — resolves OQ33, authorization (settled with Dave 2026-10-14 and 2026-10-15; built 2026-10-15 for the stored actor, `compiler/src/test/kotlin/velle/ActorTest.kt`, `examples/pharmacy/pharmacy.velle`). An act a person commits says so in its header: `act LicenceRenewal by Administrator { ... }`, `transient act FillPrescription by Staff as filledBy { ... }`. The shape after `by` is a `shape`, a static union of shapes, or a refinement of one — never an act, since an act is an input and the person who commits one is a record; a refinement there is the role gate in the header, one desugaring to `LicenceRenewal requires actor to be Administrator`, which stays legal to write in the body beside it (a two-role gate, `SetReorderPoint requires actor to be Administrator or actor to be Pharmacist`, is written that way or over a composed refinement). The clause binds the committer in the act's scope under the name `actor` unless `as` chooses another; nothing is reserved, `actor` is an ordinary identifier wherever no clause binds it, and a scope that declares a field under the bound name is told to name the actor ([`checks.md`](checks) [F3](checks#f3--position-rules)). The actor is a fact of the commit in the family of `id` and `timestamp` ([§5](Reference-05-Scalars)): never in the generated input value, never claimed by the committer, never assigned, and on a durable act stored under the bound name with nothing declared, readable through any reference to the act (`renewal.actor`) for as long as the record exists, so an `after commit` or scheduled rule over the act reads it on every firing path alike — the memory is data, and the tick law ([§17](Reference-17-Schedule-triggers)) is untouched. An act without the clause has no actor: a processor's verdict or an insurer's adjudication arrives from a machine and says nothing. The generated commit function of an act declared `by` takes the actor as a parameter beside the input (`commit(NewVerifyFill(...), pharmacist)`, a `Ref` to the base shape), and the binding hands it the record it resolved the authenticated identity to — one resolver registered once, the shape of Spring's filter rather than JAAS's per-call lookup; a missing actor, or one of the wrong base shape, is a type-level refusal, and one outside the named refinement is the requirement's refusal with the actor's record in its rejection data ([§21](Reference-21-never)). Where `actor` may be read is where the compiler can prove which act is in scope: the act's own prohibitions, refinements, and derived properties; any rule whose subject is the act or a refinement of it, at any cadence; and an `on commit` rule whose subject is a product of the transaction, which declares what it reads in its header (`rule LogQuarantine when Quarantine by Staff? { ... }`) and is typed by reachability over the condition graph ([`checks.md`](checks) [V31](checks#v31--a-rules-actor-typed-by-reachability)): `by Staff` when every path to the trigger starts at an act declared `by`, `by Staff?` when some path starts at a tick, an `after commit` firing, or an act without `by`, where the actor is absent and the body narrows with `actor is some` as it narrows any optional — "the user if there was one, or system" is `if actor is some then actor.name else "system"`, with nothing reserved for the system. There is no system identity: a spec that wants a job to commit a gated act models the job's actor as business data (a staff member with a system role) and the binding provides it as it provides a person; and a tick has no actor. Bootstrapping is not the language's problem: the first administrator of a system whose hiring act is gated on an administrator is seeded by the engineer outside the trust boundary, as a migration or fixture row is — `VelleSystem.seed` is the in-memory form, no door, no rule, no prohibition ([`evaluation.md`, "An exposed call"](evaluation#an-exposed-call)). The read side is the same person seen from the other direction ([§8](Reference-08-Refinements), "Who may see a record"; built 2026-10-15, `compiler/src/test/kotlin/velle/VisibilityTest.kt`, `examples/vendors/vendors.velle`): `visible to <Shape> [as name] [where ...]` as a body clause on a shape and after a field's type, `visible to anyone` for a public one, several clauses disjoining, a shape's own replacing the spec-wide default written once at the top; required on every readable shape once a spec has any `by` or `visible to` ([`checks.md`](checks) [V32](checks#v32--every-readable-shape-declares-its-visibility)); applied by the read surface only — `read(viewer)` on the generated system takes a reference to any shape a clause names and returns the same roots with every query carrying the viewer, every fetch resolving absent for a record the clauses do not admit, and every model object projected: one class per shape declaring each field once, a gated field nullable in it, and one interface per viewer shape per shape with gated fields listing what that viewer may see, so a screen written for staff cannot compile against a cost it may not have; the engineer's own `read` stays the unfiltered class, their view of their own store — and never inside evaluation, so a derived property is calculated from every input whoever asks ([§7](Reference-07-Derived-properties)). A refusal is handed back through the same surface: its rejection data is projected for the actor as a read would be, the act they committed whole and the records it read through without the fields they may not see. An actor built from an identity provider's claims rather than stored (`transient shape Staff`) is the remaining slice: designed (an unstored shape the resolver builds per call, correlated to stored records by a business key, [V17](checks#v17--transient-isolation) restated so nothing stored references it), built by nothing yet, and listed in QUESTIONS.md. [Reference §8](Reference-08-Refinements)'s rule stands with one step taken: a transaction has an actor and `actor` names it; what [§8](Reference-08-Refinements) still excludes is a user who exists outside any act.
- **Reversal** — resolved as a non-issue for the language itself: it's a business-policy choice, expressed via which artifact shapes a human declares. Two candidate idioms exist — the resolution artifact (now exercised as membership's delinquency episodes) and the grace-period suppression window (unexercised) — but no single canonical pattern has been adopted.
- **Escape hatch / override syntax** — how a human marks part of a spec as intentionally hand-implemented/AI-implemented rather than declarative. Deferred; agreed to be a lesser concern until the core language settles.
- **Compiled guardrails** — the idea that the compiler/transpiler should structurally enforce best practices (e.g. forced prepared statements, automatic error-context capture, correctly evaluating self-referential shape/derived-property definitions, how deep narrowing analysis for `.`-vs-`?.` sees through nested expressions, erroring — not silently resolving — a bare unqualified name that doesn't exist in its innermost scope but would resolve unambiguously in exactly one enclosing scope, per `## Principles`'s compiling-as-validation rule: the fix is always an explicit `this.field`, never an inferred scope-walk that could silently start pointing elsewhere the moment an enclosing shape gains a same-named field; a field addition that creates a new type-match ambiguity for an existing bare `for` reference elsewhere in the spec, per [§14](Reference-14-for), must be reported as one connected diagnostic naming both the declaration that introduced the ambiguity — e.g. `Referral` gaining a second `Customer`-typed field — and every reference it now makes ambiguous — e.g. `CustomerWhoReferred`'s `for this` — since the compiler's job is reporting an incoherence in the spec as a whole, not a syntax error in one isolated line, and a human should never have to search for why an untouched line stopped compiling) as a byproduct of codegen. A design principle, not yet a syntax construct — with one member now sourced by syntax: runtime boundary validation derived from the refusals and constraints `never` declares ([§21](Reference-21-never)).
- **Extensible data types** — built: an extension type is a Kotlin class registered on the classpath that a spec names like `Date`, declaring every capability a spec may use of it ([§5 "Extension types"](Reference-05-Scalars#extension-types); the [Extension types](Extension-types) guide). `Money` is `examples/billing/billing.velle`'s amount. What remains is the other half of the framework below: custom functions and predicates over the same capabilities.
- **The extension framework** — custom data types and custom functions (both built; the Extension types and Extension functions guides) are one concept wearing two hats: **registered extensions** — traditional code the developer hands the compiler at execution time through a registration API. Three commitments shape the design. **Registration carries validator-facing metadata**: an extension declares what the checks need to know about it — a custom function's algebraic properties (idempotence, duplication/reordering insensitivity: the `## Self-referential folds` whitelist generalized from a builtin table to a registration contract), a custom type's permitted operations and orderability — so the closed builtin list (`## Scalars`) becomes the *registered* list, and the validator typechecks calls and discharges fold hazards against the registry rather than a hardcoded set. **Extensions are distributable**: workspace-local custom code the compiler locates, or packaged, installable libraries — shared business-domain extensions (a "Velle finance extensions" library carrying `Money`, its operations, its literals) — the same artifact either way. **Extensions are not output**: the transpiled code lives in the developer's workspace and the developer owns it, while extensions live separately, because they change on different axes — a spec edit regenerates output but never touches extensions; an extension upgrade re-runs validation but never rewrites the spec. The resulting architecture has three parts: (1) the language + compiler/validator + environment, which locates extensions in the workspace; (2) the extension framework — types, functions, custom or packaged; (3) the transpile output — the developer-owned executable runtime, *generated executable tests that verify the runtime against the spec*, and opt-in derived diagrams ([`diagrams.md`](diagrams)).
- **`initially` generator vocabulary** — `randomUUID` is the only generator so far (`## Scalars`); whether others belong, and which, is undecided. Sequence-flavored generators stay excluded on principle — ordering comes from timestamps or declared fields, never minted values.
- **Exit from act-entered refinements** — a membership predicate of the form `exists ArchiveRequest for this` is monotone: facts persist, so nothing can ever leave `ArchivedInvoice`, and un-archiving is inexpressible. Exit requires either pairing occurrences in the predicate — the simple unordered pairing (`exists Receipt for this and not exists ReceiptVoid for this`) is expressible today and is how a `frozen` state thaws ([§8, "Frozen fields"](Reference-08-Refinements#frozen-fields-frozen)), while `... and not exists Unarchival` *newer than the matched request*, needed the moment re-archival enters the model, requires occurrence-comparison vocabulary not yet designed (its ordering source is settled — the occurrence shape's declared creation timestamp, or an author-named field — but the comparison/scoping spelling isn't) — or a mutable field the predicate reads. Both are expressible; which is idiomatic is unsettled.
- **State partition declaration** — refinement properties give states their data (`## Refinements`), `frozen` gives states their write permissions (`## Refinements`, "Frozen fields"), and reified acts give transitions their payloads — but nothing yet asserts that a set of refinements *partitions* a shape: mutually exclusive, jointly exhaustive ("an invoice is always in exactly one of Draft, Issued, Paid, Voided"). Candidate spelling `states of Invoice = Draft | Issued | Paid | Voided`, invoking the exhaustiveness/overlap check `## Refinements` already names as a compiler goal — and the natural long-term home for per-state write permissions beside legal transitions (where "this field is frozen in every state" becomes the never-writable diagnostic). `never` ([§21](Reference-21-never)) is its natural primitive: pairwise disjointness is `never (A and B)`, leaving only the coverage check. The next investigation.
- **Spec-carried examples (`example`)** — a future construct letting the spec itself declare named example instances, so generated executable specs ([`testgen.md`](testgen)) derive their scenario data from the description instead of demanding human-written givens — the description becomes self-illustrating, collapsing the given/derived split's human tier. Not yet designed; [`testgen.md`](testgen) phase 3.
- **`why` / provenance** — a command to trace which rule/refinement produced a given piece of state, mapped back to Velle source. Agreed as a goal; no syntax proposed yet.
