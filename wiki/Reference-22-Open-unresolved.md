# 22. Open / unresolved

**Current milestone — the v0 validator/transpiler (scope settled).** v0 implements §3–§21 as written — plus two constructs adopted after the original scope statement (`transient act`, §4 "Transient acts", from the transient-acts investigation; the act's closure `act ... with`, §6 "Inline part creation"; deletion and its trigger family, §12 "Deletion" and §13 "Deletion as a second exit cause", from the delete investigation) — validated and transpiled to an executable runtime driven through a test-harness boundary, itself fully settled. Input enters through the `act` construct: each `act` declaration transpiles to a typed input value — a Kotlin data class of the act's stored fields, `NewSubmitPayment` for `act SubmitPayment` — and a `commit` overload that takes it: the thing the engineer's own transport code calls to submit a mutation, and a class any transport can bind a request to by reflection with nothing written by hand — plus a generated `main`-style entry point for driving the system manually. The declaration names no mechanism; transport, persistence, and serialization are the engineer's code, outside the spec (the external-input item below). A call returns acceptance or a refusal, each carrying the input value it was handed, so a refusal holds what was refused as the engineer's own type and never as a map; a refusal names what was violated — the type-level failure or the specific `never`, the latter carrying its context as data (§21) — and on refusal nothing commits. Refusal is whole: the unit accepted or refused is the closure the commit would have been (§4), never a part of it, so a request that should succeed in part is submitted as separate acts, or lands whole with its refused subset an ordinary refinement the rules answer (§2, the errors-are-refinements pattern; §4 "Every request gets a response"). Ticks enter the same way — each schedule name transpiles to a tick function the harness calls, since scheduled events and user acts are both external input (§4, §17) — so schedule definition is not needed; when that construct lands, it defines *when* the tick functions are called, never what they do. Reading is **a query API the caller composes, over model objects**: every shape and refinement has a generated data class, the model object, every field read once at the moment of the read; a model object is itself a reference to its record (`Ref<Invoice>`, one type for both sides of the store boundary — a store row carries the same thing for each to-one field), so it passes wherever a reference is taken, equal to any other reference to the same record — equality is identity, and comparing fields is how an engineer asks whether two reads differ; a reference field holds a `Ref<T>` and `read(ref)` resolves it; and a query over any shape or refinement is composed by the caller from the spec's declared vocabulary (properties, references and inverses, refinement membership, the predicate language of §10, a required order over orderable datums, a page), returning model objects. A store key fetches one instance by identity the same way. Nothing is read *through* a reference: a view with getters would be a second, live read path beside the snapshot, and there is one. The spec declares definitions, never a query: a question a screen asks is written by whoever asks it, checked against the spec, and is not a line in the spec (OQ51, 2026-10-12). Querying is "read" in §4's sense and commits nothing. Built: the read protocol and its engine (`compiler/src/main/kotlin/velle/Read.kt` — a query as a value, checked by the validator's own predicate rules, answered from a read-only snapshot, ordered with the store key as the hidden tie-break, paged by cursor, counted and summed), the generic entry beside `commit` on the runtime, and per spec the typed Kotlin builder (`read.invoices.where { balance gt 0 }.orderBy { due.ascending }.page(20).fetch()`, `read(inv.customer)`, `read.invoice(key)`), one model object per shape and refinement (a static union is an interface its operands implement; a membership flag per refinement over the same base), and a registry for queries the engineer names (`examples/billing/output/src/test/kotlin/velle/QueryApiTest.kt`). Deferred past v0, with their items below: Mapping, schedule definition, the `act` construct's remaining details, the state partition declaration, extensible data types, and `why`/provenance — plus `visible to ... where`, removed from §10 until re-derived and synced. Nothing cut is exercised by any current example, and each re-enters post-v0 through its own item. - **State change & rule mechanics — remaining frontier.** The core is settled — assignment and one-writer (§12), deletion as a mutation whose legality is derived (§12 "Deletion") with its own exit cause (§13 "Deletion as a second exit cause"), run-once guards with no sugar (§18), folds and `tolerates` (§19), the pattern spectrum and rung recognition (§20), and "what is one commit": a commit is exactly one statically-shaped closure — one act instance in the common case, the container plus its declared inline parts otherwise (§4; §6 "Inline part creation") — a body is one commit, consequences share the act's transaction by default, `after commit` declares a boundary, and the irreducible world/state gap at an external effect is answered by the intent-before-effect pattern (§4, `## rule` "Transactions and `after commit`"); commit timestamps are author-declared, language-populated fields (`timestamp on create` / `on update`, §5); every instance carries an opaque, readable `id` (§5); a rule fires once per matching record — no loop construct, transaction scope following the trigger source (§16, §17); all-or-nothing batches need no envelope construct — they dissolve into one-body effects, commit-shared fan-out, one-fact-many-readers, containers, and completeness gates (§20, "All-or-nothing batches"); cascades nest as trees of transactions; `tolerates loss` signs fire-and-forget external effects (§11, §19); and `never` declares impossible configurations — transaction-end enforced, proven for guarantees, compiled into the boundary for refusals and constraints (§21); and shapes are marked externally committable by `act` declarations — the trust boundary — with the construct's remaining details deferred ("External input," below; resolves OQ5); and an exit rule is the last reader of the leaving refinement's captures — retraction lands at the exit commit's close, full pre-state access is rejected, and capture-reading rules are transaction-bound (§13; resolves OQ7's exit-read thread, with its two remaining threads moved below). Still open: the order-independence/confluence and quiescence proofs (OQ16). Refusal is settled: it is compiled boundary code from `never` (§21), whole and pre-commit (the scope statement above), and who-may-commit lives in engineer wrapper code ("External input" below). Ordered folds and firing order at a tick was OQ15, settled: rules carry no ordering clause — the predecessor recurrence is the served spelling (§19), and growing its certificate whitelist folded into OQ16's calibration as one shared vocabulary. Whether the canonical guard form is pleasant enough to be what fold diagnostics ask authors to write was OQ14, settled: it is — the canonical form stands as the diagnostics' fix-it spelling, no sugar added (§18).

- **External input (`act`)** — resolves OQ5, "marking a shape as external input." Velle implements no transport: REST APIs, GraphQL, socket connections to a message bus are traditional-code territory it doesn't compete in; what it owns is the contract between the spec and the shape of the transpiled code. The construct names no mechanism (it originally carried a `using <Mechanism>` clause over transpilation plugins, dropped when the runtime model settled): transpilation generates one typed input value and one `commit` overload per act — the thing the engineer's own transport code calls to submit a mutation — and mapping any transport onto those input values is the engineer's code, permanently, not a deferred plugin design. An act is declared in exactly one place, where its fields are (`act CorrectEmail { ... }`): the keyword is the shape declaration plus the boundary, not the act-level sugar §12 rejects — nothing is hidden and no positional invariant is spent — and there is no second statement that opens a `shape` declared elsewhere (OQ50, settled 2026-10-12). An act is externally committable; a `shape` enters state only as a rule's effect. The set of `act` declarations *is* the trust boundary: the `never` guardrails for refusals and constraints (§21) compile to the generated surface at each act's boundary, and reachability sharpens — a `shape` with no producing rule is uncommittable, so a rule triggered by it is the unfireable-rule error (§11). Who-may-commit conditions (caller identity, ambient policy, rate — OQ20's residue) live in the engineer's wrapper code before the commit call, outside the language. Which fields the committer supplies is read off the declaration forms — there is no field policy to state (resolves OQ31); a closure declaration (`act ... with`, §6 "Inline part creation") extends the same reading to inline parts, each a nested input value carrying every stored field minus the language-populated back-reference. The generated input value carries every stored field of the act: the committer supplies them all, an optional (`?`) field by explicitly supplying the absence, and a convenience default belongs in the engineer's wrapper before the commit call, with the transport mapping it already owns. Derived properties are legal on an act and are never fields of the input — nothing is stored, so there is nothing to supply, and the `= expression` form states in the language that the value is calculated (on a transient act, whose one evaluation moment is its own commit, a derived property is also how an arrival-time value is fixed). `initially` and `timestamp` declarations on an act are compile errors (`checks.md` V21): a system-maintained value is no part of an external submission, so it lives on a `shape` — supplied by a materializing rule's `from` block, minted by `initially` at that record's creation commit, or populated as `timestamp` commit metadata — with the transient-act materialization (§4) as the served spelling for a request whose durable record carries such fields. Still deferred as details of the construct, not open language questions: supplied-vs-generated `id` at a trust/legacy boundary (a legacy table's primary key, an upstream system's reference — mapping-side mechanics ride with the Mapping item, above). `act` is strictly input (OQ51, 2026-10-12): reading never goes through an act.
- **Reversal** — resolved as a non-issue for the language itself: it's a business-policy choice, expressed via which artifact shapes a human declares. Two candidate idioms exist — the resolution artifact (now exercised as membership's delinquency episodes) and the grace-period suppression window (unexercised) — but no single canonical pattern has been adopted.
- **Escape hatch / override syntax** — how a human marks part of a spec as intentionally hand-implemented/AI-implemented rather than declarative. Deferred; agreed to be a lesser concern until the core language settles.
- **Compiled guardrails** — the idea that the compiler/transpiler should structurally enforce best practices (e.g. forced prepared statements, automatic error-context capture, correctly evaluating self-referential shape/derived-property definitions, how deep narrowing analysis for `.`-vs-`?.` sees through nested expressions, erroring — not silently resolving — a bare unqualified name that doesn't exist in its innermost scope but would resolve unambiguously in exactly one enclosing scope, per `## Principles`'s compiling-as-validation rule: the fix is always an explicit `this.field`, never an inferred scope-walk that could silently start pointing elsewhere the moment an enclosing shape gains a same-named field; a field addition that creates a new type-match ambiguity for an existing bare `for` reference elsewhere in the spec, per §14, must be reported as one connected diagnostic naming both the declaration that introduced the ambiguity — e.g. `Referral` gaining a second `Customer`-typed field — and every reference it now makes ambiguous — e.g. `CustomerWhoReferred`'s `for this` — since the compiler's job is reporting an incoherence in the spec as a whole, not a syntax error in one isolated line, and a human should never have to search for why an untouched line stopped compiling) as a byproduct of codegen. A design principle, not yet a syntax construct — with one member now sourced by syntax: runtime boundary validation derived from the refusals and constraints `never` declares (§21).
- **Extensible data types** — author-declared scalar types beyond the builtin list (`## Scalars`). `Money` is the canonical example, demoted from builtin when the scalar list was pinned to Kotlin-grounded types: currency, precision, and literal syntax are exactly the kind of domain judgment an author should declare, not a builtin should assume. What declaring one means — underlying representation, permitted operations, how `sum` and comparisons extend to it — is undesigned. The examples keep using `Money` as a preview of the capability. One citizen of the extension framework, below.
- **The extension framework** — custom data types (above) and custom predicate/value functions are one concept wearing two hats: **registered extensions** — traditional code the developer hands the compiler at execution time through a registration API. Three commitments shape the design. **Registration carries validator-facing metadata**: an extension declares what the checks need to know about it — a custom function's algebraic properties (idempotence, duplication/reordering insensitivity: the `## Self-referential folds` whitelist generalized from a builtin table to a registration contract), a custom type's permitted operations and orderability — so the closed builtin list (`## Scalars`) becomes the *registered* list, and the validator typechecks calls and discharges fold hazards against the registry rather than a hardcoded set. **Extensions are distributable**: workspace-local custom code the compiler locates, or packaged, installable libraries — shared business-domain extensions (a "Velle finance extensions" library carrying `Money`, its operations, its literals) — the same artifact either way. **Extensions are not output**: the transpiled code lives in the developer's workspace and the developer owns it, while extensions live separately, because they change on different axes — a spec edit regenerates output but never touches extensions; an extension upgrade re-runs validation but never rewrites the spec. The resulting architecture has three parts: (1) the language + compiler/validator + environment, which locates extensions in the workspace; (2) the extension framework — types, functions, custom or packaged; (3) the transpile output — the developer-owned executable runtime, *generated executable tests that verify the runtime against the spec*, and opt-in derived diagrams (`diagrams.md`).
- **`initially` generator vocabulary** — `randomUUID` is the only generator so far (`## Scalars`); whether others belong, and which, is undecided. Sequence-flavored generators stay excluded on principle — ordering comes from timestamps or declared fields, never minted values.
- **Exit from act-entered refinements** — a membership predicate of the form `exists ArchiveRequest for this` is monotone: facts persist, so nothing can ever leave `ArchivedInvoice`, and un-archiving is inexpressible. Exit requires either pairing occurrences in the predicate — the simple unordered pairing (`exists Receipt for this and not exists ReceiptVoid for this`) is expressible today and is how a `frozen` state thaws (§8, "Frozen fields"), while `... and not exists Unarchival` *newer than the matched request*, needed the moment re-archival enters the model, requires occurrence-comparison vocabulary not yet designed (its ordering source is settled — the occurrence shape's declared creation timestamp, or an author-named field — but the comparison/scoping spelling isn't) — or a mutable field the predicate reads. Both are expressible; which is idiomatic is unsettled.
- **State partition declaration** — refinement properties give states their data (`## Refinements`), `frozen` gives states their write permissions (`## Refinements`, "Frozen fields"), and reified acts give transitions their payloads — but nothing yet asserts that a set of refinements *partitions* a shape: mutually exclusive, jointly exhaustive ("an invoice is always in exactly one of Draft, Issued, Paid, Voided"). Candidate spelling `states of Invoice = Draft | Issued | Paid | Voided`, invoking the exhaustiveness/overlap check `## Refinements` already names as a compiler goal — and the natural long-term home for per-state write permissions beside legal transitions (where "this field is frozen in every state" becomes the never-writable diagnostic). `never` (§21) is its natural primitive: pairwise disjointness is `never (A and B)`, leaving only the coverage check. The next investigation.
- **Spec-carried examples (`example`)** — a future construct letting the spec itself declare named example instances, so generated executable specs (`testgen.md`) derive their scenario data from the description instead of demanding human-written givens — the description becomes self-illustrating, collapsing the given/derived split's human tier. Not yet designed; `testgen.md` phase 3.
- **`why` / provenance** — a command to trace which rule/refinement produced a given piece of state, mapped back to Velle source. Agreed as a goal; no syntax proposed yet.
