# OQ70 — A unit of work in the store contract: pooled connections, a transaction per read, and the queue keys taken where the database can see them

**Status:** opened 2026-10-27 at Dave's request, after the Spring Boot starter (built 2026-10-26) showed the cost of the current shape: `SqlStore` holds one `java.sql.Connection` for the system's life, and the API layer serializes every commit, tick, and read on one process-wide lock. Decisions D1–D6 below were ratified by Dave 2026-10-27 ("your recommendations sound right to me"). Sequencing, also Dave's: the store side lands first, and the second half of D1 (the working set per unit of work, then `VelleApi`'s one lock replaced by per-key admission) is tackled right after, not deferred. The store side is built 2026-10-27 (items 1–7 below, all tests green over SQLite and PostgreSQL): `StateResolver.begin(kind)` returns a `UnitOfWork` with `serialize(keys)` and `end(outcome)` (`WorkKind`, `Outcome`, `AdmissionKey` in `Hydration.kt`, defaults for a store with nothing to open); the runtime opens a read unit lazily at a query's first fetch and closes it at the outermost scope's exit or when an envelope opens, opens a write unit in `inTransaction` and `seed`, values the envelope's queue keys at admission (`actKeys`, `firingKeys`, hopping stored and captured members; `DomainAnalysis.firingDomains` now covers every rule so after-commit firings have a domain), hands them to `serialize`, drops the working set, and ends the unit with the outcome; `SqlStore` takes a `DataSource` and a connection per unit (`OneConnection` wraps a single connection for SQLite in memory), `SqlDialect` gained `prepare`/`beginRead`/`beginWrite`/`lock`/`serializesKeys`, PostgreSQL takes transaction-scoped advisory locks on `hashtext(key)` in sorted order under `lock_timeout`, SQLite begins deferred for a read and immediate for a write; the generated typed store forwards `begin` (`StoreGen`, all examples regenerated); the conformance suite runs SQLite over a temporary WAL file and PostgreSQL over an unpooled `DataSource` per schema and pins: one connection per unit returned at its end, a read's snapshot while another connection commits, a refusal writing nothing, two envelopes on one key taking turns and disjoint keys not waiting, a lock timeout failing the envelope. What remains is the second half of D1.
**In plain terms:** today a Velle system over a database borrows one connection at startup and never gives it back, and the web layer lets one request at a time touch the system. That works for a developer's machine and fails in production: a dropped connection is fatal until restart, two copies of the application can interleave at the database, and nothing can run in parallel. The fix is to let the store know when a piece of work begins and ends, in Velle's own words, so the SQL store can take a pooled connection and a transaction for exactly that long, and take the locks the spec's own analysis says the work needs. The runtime must still import nothing from SQL.
**v0 stance:** the global lock in `VelleApi` stays only until the runtime's working set is per unit of work (D1); the store side landed first (2026-10-27), the lock's replacement is next.

## 1. What exists

**The runtime is single-threaded by construction, not by contract.** `VelleSystem` has no lock, no synchronized block, and no thread-safe collection. With a store connected, `instances`, `byShape`, the fetch caches, and `captures` are one shared working set over the database; `beginSnapshot` empties it so the next fetch returns to the store. A commit faults rows into that set, applies its mutation set to it, and hands the set to `onCommit` inside the envelope. A read calls `openReadSnapshot`, which clears the set only when no envelope is open (`txn == null`). Two threads in the runtime at once therefore either read an envelope's half-applied state or clear the maps an envelope is using. The lock in `VelleApi.locked` is the only thing preventing that; the generated commit functions and the typed query surface do not lock.

**The store holds one connection.** `SqlStore(model, conn, dialect, bindings)` takes a `Connection`. `onCommit` turns `autoCommit` off, writes, commits or rolls back, turns it back on. Every fetch is an autocommit statement on the same connection. So: a read is consistent within one process only because the lock keeps the process quiet; a second instance of the application, or any other writer, can change rows between two fetches of one read; a dropped connection is not reconnected; HikariCP sees one connection permanently checked out; even with per-key serialization, two non-conflicting commits could not run at once.

**The queue keys exist at compile time only.** `Domains.kt` derives each act's and each scheduled firing's domain (`QueueKey.Path`, `QueueKey.ValueOf`, `Widening`). They reach the engineer as the generated commit function's KDoc ("Queue keys: [deposit.account]") and the contention map. Nothing at runtime evaluates a key's concrete value at admission; `Runtime.kt` does not mention them.

**The boundaries the store would need are already in the runtime.** `scope` at depth zero is one read (it clears the working set and the handle tables on exit). `inTransaction` is one commit or tick envelope (`beginSnapshot`, `Txn`, `checkNevers`, `onCommit`, `finalizeDeletes`, `drainAfterQueue`). A `scope` opened inside an envelope reads the envelope's state, which is right and stays.

## 2. The shape of the change

The contract grows by one idea, in the runtime's vocabulary. A sketch, not a signature:

```kotlin
interface StateResolver {
    fun begin(work: Work): WorkHandle            // Work.Read, or Work.Write
    fun serialize(work: WorkHandle, keys: Set<ConcreteKey>)   // write only, once the runtime has the keys' values
    fun end(work: WorkHandle, outcome: Outcome)  // Committed, Refused, Failed
    // fetchByKey, fetchAll, fetchReferencing, fetchCandidates, fetchCaptures: unchanged
}
```

- The runtime calls `begin` when `scope` enters at depth zero or an envelope opens, and `end` when it leaves. `onCommit` stays a separate callback, called between `serialize` and `end`, so the dialects' write path does not change.
- The SQL store implements `begin` as taking a connection from a `DataSource` and opening a transaction, `serialize` as taking one lock per key (PostgreSQL advisory locks; SQLite has one writer and needs nothing), `end` as commit or rollback and returning the connection. A connection, a pool, a transaction, and a dialect appear in `stores/sql` and nowhere above it.
- The in-memory runtime (no resolver) implements the same moments with in-process locks per key, or nothing until D1's second half lands.
- A store that is a REST call, a queue, or a file does what is honest for it, which may be nothing. The contract names the moments; the store decides what a moment costs. That is the rule `evaluation.md` already states for serialization, given a place in the contract.

## 3. Decisions (proposed and ratified 2026-10-27)

- **D1 — Scope: the store unit of work first, the global lock stays.** Pooled connections, reconnection, and a consistent read per request come from the store side alone. Letting two non-conflicting units run at once also needs the runtime's working set (`instances`, `byShape`, the caches, the handle tables) moved off `VelleSystem`'s fields into an object created at `begin` and dropped at `end`. That is a refactor inside `Runtime.kt` with no new imports, separable, and second.
- **D2 — Two calls for a write: open the unit, then take the keys.** A key's value is computed at admission against pre-commit state and may hop through a captured member (`reopenTicket.ticket.closedBy`), so the unit must be open before the keys exist. Hence `begin`, then `serialize(keys)` once computed, then `onCommit`, then `end`. After `serialize` returns the runtime clears its working set, so everything it evaluates was read after the locks were held. **This decision carries new runtime work:** evaluating `QueueKey.Path` and `QueueKey.ValueOf` to concrete values at admission does not exist today (§1); the compile-time derivation is in place, the runtime side is not.
- **D3 — Isolation: a read is a snapshot, a write is read committed.** A read unit opens a read-only snapshot transaction (REPEATABLE READ in PostgreSQL; SQLite's deferred transaction), which is what "one consistent state" in U1 means for a read. A write cannot be a snapshot taken before its locks, since what it then reads could be stale, so it runs read committed and relies on D2 for freshness.
- **D4 — Keys are locked in the database, in sorted order, waiting with a timeout.** Advisory locks per key in PostgreSQL, so two processes serialize correctly. Sorting the keys before taking them avoids deadlock between two commits with overlapping sets. A timeout turns a stuck lock into a failed commit (a `Failed` outcome, U2's in-envelope failure) rather than a hung request; the number is a store setting, never a spec concern. A `Widening` locks the shape's name. The in-memory store mirrors this with in-process locks.
- **D5 — `SqlStore` takes a `DataSource`; the `Connection` constructor goes.** One construction path means the conformance suite tests the real one. Tests build a `DataSource` over their SQLite URL. The starter's `attach` passes the application's `DataSource` through and reads the product name once to pick the dialect.
- **D6 — This is an OQ**, absorbing the first two residue items under QUESTIONS.md "Serving" (the one lock; the one connection). It stays open until D1's second half lands; Dave wants that done right after the store side, so it is not split out.

Two things need no decision because the current behavior is right: a `scope` inside an envelope reads the envelope, so `begin` fires at depth zero only; a refused commit ends its unit with a rollback, and any refusal record it writes (a `never` that records rather than refuses, Reference §21) goes through `onCommit` as today.

## 4. Items

- [ ] The second half of D1: the working set (`instances`, `byShape`, the fetch caches, `captures`, and the handle tables) per unit of work inside `Runtime.kt`, held by an object created at `begin` and dropped at `end`, so two units run at once on two threads; then replace `VelleApi`'s one lock with admission through the store's `serialize` (in memory: a lock per key in the runtime, since `UnitOfWork.None` serializes nothing); `SqlStore.current` is already a `ThreadLocal`, so the store side needs no change; update the wiki `API-layer` page's "The layers" and "One request, end to end" sections and `Serving-a-system`'s `api.locked` bullet, which describe the lock.
- [ ] Decide what a read issued outside any `scope` does over a store: today it opens a read unit that the next scope exit or envelope closes, which holds a pooled connection until then; refusing it, or closing the unit at the end of the call, are the alternatives.
- [ ] A value key (`QueueKey.ValueOf`) on a scheduled or after-commit firing takes the shape's width today, because the committed value is not known before the firing runs; evaluate the firing's creation values at admission instead where the rule body allows it.
