# OQ67 — The store API in two layers: an agnostic store API the runtime speaks, and a SQL store API Velle implements on top of it

**Status:** opened 2026-10-24 at Dave's request while settling OQ65 D5. Nothing designed past the statement of the split and what exists today.
**In plain terms:** today one class, `SqliteStore`, does two jobs at once: it answers the runtime's questions (fetch a row, scan a shape, follow a reference, write a commit) and it knows SQL (tables, columns, `WHERE` clauses, SQLite's own types). The first job is the same for every store. The second is the same for every SQL database and differs only in dialect. Dave's direction: split them. An *agnostic store API* hands a store every object Velle's commit and fetch produce and consume, with no SQL in it. A *SQL store API*, implemented once by Velle over those agnostic objects, does the table-and-column work for any SQL database. `SqliteStore` then implements the SQL store API, not the agnostic one, and shrinks to its dialect. A system tells the compiler which API its store provides, so the compiler can check and generate against the right layer.
**See:** the store binding for an extension type as built (`stores/sql/src/main/kotlin/velle/sql/SqlTypeBinding.kt`; E4 in `SqlStore`; the wiki guide `Extension-types`, "Holding a type in a store"): a binding at the SQL layer would serve every SQL store, one at the SQLite layer only SQLite · OQ59 (the typed store as the one built escape hatch) · Reference §22 "The extension framework" (the architecture's three parts; `stores/sqlite` as "the framework role") · `evaluation.md` (the universal transaction U1–U5 a store honours) · `compiler/src/main/kotlin/velle/Hydration.kt` (`StateResolver`, `CommitCallback`, `Row`, `CommitSet`, `StoreKey`, `CaptureSchema`), `Query.kt` (`QF`, the compiled pre-filter), `StoreGen.kt` (the generated typed store), `stores/sql/src/main/kotlin/velle/sql/SqlStore.kt` (the layer), `SqlDialect.kt` (what a database contributes), `stores/sqlite/src/main/kotlin/velle/sqlite/SqliteDialect.kt`.

---

## 1. What exists

- **The agnostic layer already exists in substance.** `StateResolver` (fetch by key, scan, join read, filtered scan over a `QF`, capture read) and `CommitCallback.onCommit(CommitSet)` are SQL-free; `Row`, `StoreKey`, `Ref.Persisted`, `CommitSet` with its creations, assignments, captures, retractions, and deletions, `CaptureSchema`, and `QF` are the objects. The universal transaction (`evaluation.md` U1–U5) is stated against them. What it lacks is a name as a layer and a statement that it is the whole of what a store must provide.
- **The SQL layer does not exist.** `SqliteStore` renders `QF` to SQL (`render`, `renderCmp`, the `LIKE` escape), maps `VType` to column types (`sqlType`), creates tables (`createSchema`, membership tables for `many`, capture tables, the union discriminator column), reads and writes columns (`readColumn`, `writeColumn`), encodes constants for push-down (`encode`, degrading what TEXT cannot order), and keys rows on `INTEGER PRIMARY KEY AUTOINCREMENT`. Nearly all of that is SQL, not SQLite; the dialect is the key strategy, the type names, the `LIKE` case folding, and the connection.
- **The typed store** (`StoreGen`) is generated per spec on top of `StateResolver`: an interface of the spec's own questions, a default implementation over any generic backend, and a resolver bridge. It is agnostic today and should stay so; a SQL-layer typed store (hand-tuned SQL per question) is the escape hatch OQ59 describes.

Dave's stance on stores generally (2026-10-24, while settling OQ65 D5): ideally there is one store implementation, because object-relational mapping is a solved problem; Velle *provides* that store and does not *force* it on a system. "When it comes to custom data types, the engineer is explicitly saying they have a custom data layer that they need to fit velle onto. That means dealing with the store." Set aside with it: a type carrying a *carrier*, one of Velle's builtins it encodes itself to so that every store holds it with no new code; it cannot cover the world's types and turns a word the product owner and engineer share into a mapping exercise.

## 1a. The motivation, measured (2026-10-26)

Dave's motivation for the split: how much a PostgreSQL store and the SQLite store would share through a middle relational store, and which SQL helpers would be refactored into it. An inventory of `SqliteStore` (630 lines) sorted by what a second dialect would reuse:

- **Shared by any relational store, about three quarters.** Model-to-schema (columns per shape, junction tables for collections, the union discriminator column, a capture table per refinement, the naming of all three); every read (by key, scan, join read, capture read, row assembly, collection reads); the whole `WHERE` renderer (polarity degrade, null-inclusive `!=`, `EXISTS` for reference hops, union back-reference matching key and shape, `LIKE` escaping); the whole commit (one transaction, creates in order against minted keys, whole-set collection replacement, capture upsert and retraction, deletions last with the absorbing reference left in place); the E4 round-trip check. Every correctness argument in the store lives here, which is the strongest reason for the layer: a standalone second store would re-derive the superset contract, the null semantics, and the deletion order, not merely retype SQL.
- **Dialect, about a quarter.** Column type per builtin (SQLite is forced to `TEXT` for decimal, date, datetime, uuid, time and `INTEGER` for boolean; PostgreSQL has native types for each) and the read and write of each; which comparisons a column answers (decimal and datetime degrade today only because `TEXT` does not order as the value does, PostgreSQL answers them natively); key minting (`AUTOINCREMENT` + `last_insert_rowid()`, but both engines support `INSERT ... RETURNING id`, so it can be unified rather than abstracted); capture upsert (`INSERT OR REPLACE` versus `ON CONFLICT DO UPDATE`, also unifiable since SQLite 3.24); `LIKE` case folding (SQLite folds, PostgreSQL does not; the dialect need only say whether the rendering is exact); regular expressions (OQ69); identifier quoting (the same double quote in both).
- **A portability bug the split surfaces.** Collection order is read with `ORDER BY rowid`; PostgreSQL has no `rowid`. A portable junction table needs an explicit position column, owned by the SQL layer.
- **The dialect interface, in substance.** Everything in the dialect list except key minting and regex is "for this builtin type: column type, bind, read, which comparisons it answers", which is what `SqliteTypeBinding` already is for extension types. So a dialect is a binding per builtin type plus a key strategy, and the SQL layer treats builtins and extension types through one binding interface (OQ68's direction; Velle coding to its own extension interfaces). The one real design decision: a binding cannot name a dialect's column type directly, so either the binding names an abstract storage class (text, integer, decimal, bytes) that the dialect maps to a name, or `SqlTypeBinding<T>` is per dialect after all.

## 1b. Built 2026-10-26: the SQL layer with SQLite as its one dialect

- **`stores/sql`** (`velle.sql`): `SqlStore` is the whole of yesterday's `SqliteStore` minus SQLite: the model-driven schema, the reads, the `WHERE` renderer with its polarity and null rules, the commit, E4. `SqlDialect` is what a database contributes: `name`, `keyColumn` (the DDL after `id`), `column(StorageClass): StorageColumn`, `regexMatch(column)`. `StorageClass` is the eleven kinds of column with one carrier each (text/String, integer/Long, decimal/BigDecimal, double/Double, boolean, date, datetime, time, duration, uuid, bytes); every builtin scalar has one of its own with the value as carrier, and `SqlTypeBinding<T>` (`type`, `storage`, `encode` to the carrier, `decode` from it, `answers`) names one for an extension type. Builtins and extension types go through one path (`SqlStore.scalarColumn`), the dialect's `StorageColumn` for the class; a comparison is pushed down only when both the binding and the dialect's column answer it.
- **`stores/sqlite`**: `SqliteDialect(conn)` (the eleven columns, `AUTOINCREMENT`, the `REGEXP` function) and `SqliteStore` as a two-line subclass keeping `attach` and the constructor every example test calls. `SqliteTypeBinding` is gone.
- **`extensions/finance-sql`** (was `finance-sqlite`): `SqlMoneyBinding` with `StorageClass.INTEGER`, registered in `META-INF/services/velle.sql.SqlTypeBinding`; `MoneyOverSqliteTest` runs it over the SQLite dialect.
- Behaviour kept bit for bit where the examples look: every example's store test and the Money tests pass unchanged (the enrollment test's direct `ORDER BY rowid` on junction tables became `ORDER BY pos`). Three deliberate changes inside: scans carry `ORDER BY id` (SQLite's rowid order made explicit, so every dialect gives creation order); boolean and uuid columns answer `==`/`!=` only (the language has no ordering on them, so nothing observable); a text operator is pushed down only on a `text` column.
- **Chosen while building, to revisit with the second dialect:** builtin `double` rides the `DECIMAL` class (exact, as before; `DOUBLE` exists for a binding that wants a floating column); SQLite's datetime column answers nothing because `Instant.toString` varies its fraction digits, a fixed-width format would let it answer all six; the dialect is built per connection because SQLite installs `REGEXP` on it; E4 round-trips through the dialect's column, so it is per dialect by construction and also checks that `encode` returns the class's carrier.
- **Built later the same day: PostgreSQL and the conformance suite.** `stores/postgres`: `PostgresDialect` (an object: `BIGINT GENERATED ALWAYS AS IDENTITY` keys; TEXT, BIGINT, NUMERIC, DOUBLE PRECISION, BOOLEAN, DATE, TIMESTAMPTZ, TIME, BIGINT seconds, UUID, BYTEA; every class answers all six comparisons but boolean and uuid; `matches` left to the evaluator, see OQ69) and `PostgresStore`. `SqlStoreConformance` in `stores/sql`'s test fixtures is the scenarios every dialect must pass over a real database (every builtin and collection round-trip across processes, absent optionals, each comparison pushed down exactly when the dialect's column answers it, union-typed references and the join read, capture memory with re-entry and retraction, deletion with the absorbing reference, E4 three ways); `stores/sqlite` runs it in memory, `stores/postgres` in a Testcontainers PostgreSQL (`PostgresTesting`: one container per JVM, a schema per connection, skipped without Docker). Billing, enrollment, and gallery re-run their generated flows over PostgreSQL the same way. Two things the second dialect changed in the layer: the renderer emits `TRUE`/`FALSE`, not `1`/`0`, since PostgreSQL's `WHERE` takes only booleans; and the layer no longer reads a text constant as a uuid or time, because `Query.kt` never produced one — `tryCmp` dropped `opensAt < "09:00"` from the pre-filter altogether (`typesMatch` wanted a text column), which the suite caught and the compiler now reads as the type (Reference §5), `QueryCompilerTest`.
- **Not yet:** the wiki Store API page rewritten around the layer (only the sentences that named deleted things were corrected); where the layer a system provides is declared to the compiler; the typed store per layer; function renderings per layer (OQ69).

## 2. The split, as stated

1. **Agnostic store API** (`velle.store`, in `compiler/` or its own module): `StateResolver` and `CommitCallback` as they are, named as the contract; every object they exchange; nothing about tables. A store over a binary protocol, a document database, or memory implements this and only this.
2. **SQL store API** (`stores/sql`, new): Velle's one implementation of the agnostic API over the SQL vocabulary: a schema derived from the model (tables, columns, membership tables, capture tables, discriminators), `QF` rendered to `WHERE`, rows read and written through JDBC, constants bound. What it leaves abstract is the dialect: column type names, key generation, `LIKE` semantics, identifier quoting, which comparisons a column type answers.
3. **`SqliteStore`** implements the dialect of the SQL store API and nothing else. A Postgres store is another dialect, mostly type names.
4. **The store API a system provides is given to the compiler.** The output module says which layer its store implements; the compiler and the generators use it: `StoreGen` can emit the SQL-layer typed store as well as the agnostic one; OQ65's E4 checks extension-type bindings against the right layer, so a `SqlTypeBinding<Money>` (column type and JDBC read/write) serves every SQL dialect and Bob writes it once, while a dialect-level binding is only for that dialect.

## 3. What has to be settled

- **Where the layer is declared.** A Gradle dependency alone (`stores:sql` on the classpath), a line in the output module's generate task, or a value handed to `GeneratedSystem`. The spec never says it (Reference §22: the declaration names no mechanism).
- **The dialect interface** — built 2026-10-26 as `SqlDialect`/`StorageColumn` (§1b), provisional until PostgreSQL has implemented it. Was stated as: the minimum `SqliteStore` needs to shrink to: type names per `VType` and per extension-type binding, key strategy, `LIKE` escape and case behaviour, identifier quoting, the set of comparisons each column type answers. Whether schema creation is the SQL layer's (model-driven DDL) or the engineer's (migrations), with the SQL layer checking the schema it finds.
- **Extension-type bindings per layer** — settled 2026-10-26 (Dave): `SqlTypeBinding<T>` at the SQL layer names an *abstract storage class* instead of a column type, and each dialect maps the class to its own column type. Provisional classes, one per encoding `SqliteStore` uses today: text, integer (64-bit), decimal, double, bytes. The rest of the binding is as today (`type`, `bind`, `read`, `answers`), so Bob's `Money` binding (an integer of cents) is written once and serves SQLite (`INTEGER`) and PostgreSQL (`BIGINT`) alike; `extensions/finance-sqlite` becomes `extensions/finance-sql`. Still open: whether a dialect may override a binding, and at which layer E4 runs (the round-trip is per dialect, since the column is).
- **Order of work** — settled 2026-10-26: extract the SQL layer first with SQLite as its only dialect, every example's `*OverSqliteTest` green throughout, then PostgreSQL as the second dialect, then the wiki. Before extraction, three in-place changes to `SqliteStore` so the leftover dialect is minimal: `INSERT ... RETURNING id` for `last_insert_rowid()`, `ON CONFLICT (id) DO UPDATE` for `INSERT OR REPLACE`, an explicit position column on junction tables for `ORDER BY rowid`.
- **Inline bindings and shipped bindings.** Whether the store Velle provides lets the system's engineer register a type's mapping inline, as a pair of lambdas handed to the store, instead of as a binding library, and whether Velle ships bindings for common types (`Money`, a UUID, a URL) with its store.
- **The typed store per layer.** Whether `StoreGen` emits a SQL-layer variant whose default methods are the SQL layer's rendering, so an engineer's override is a hand-written SQL string for one question (OQ59's escape hatch) with every other question still generated.
- **Function renderings per layer.** Which functions a spec calls render at the SQL layer (`TRIM`, `LOWER`, `LENGTH`) and which only in a dialect (`REGEXP`, `strftime`), and how a dialect installs a function on its connection, is OQ69's; this file only places each rendering at a layer.
- **Transactions.** The universal transaction is stated on the agnostic API; the SQL layer owns the JDBC transaction and the agnostic layer's contract says what a non-SQL store owes instead.
- **The tests** — built 2026-10-26: every example's `*OverSqliteTest` runs against the SQL layer with the SQLite dialect unchanged; `SqlStoreConformance` is the layer's own suite, run by both dialect modules (§1b).
