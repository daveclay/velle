# OQ67 — The store API in two layers: an agnostic store API the runtime speaks, and a SQL store API Velle implements on top of it

**Status:** opened 2026-10-24 at Dave's request while settling OQ65 D5. Nothing designed past the statement of the split and what exists today.
**In plain terms:** today one class, `SqliteStore`, does two jobs at once: it answers the runtime's questions (fetch a row, scan a shape, follow a reference, write a commit) and it knows SQL (tables, columns, `WHERE` clauses, SQLite's own types). The first job is the same for every store. The second is the same for every SQL database and differs only in dialect. Dave's direction: split them. An *agnostic store API* hands a store every object Velle's commit and fetch produce and consume, with no SQL in it. A *SQL store API*, implemented once by Velle over those agnostic objects, does the table-and-column work for any SQL database. `SqliteStore` then implements the SQL store API, not the agnostic one, and shrinks to its dialect. A system tells the compiler which API its store provides, so the compiler can check and generate against the right layer.
**See:** the store binding for an extension type as built (`stores/sqlite/src/main/kotlin/velle/sqlite/SqliteTypeBinding.kt`; E4 in `SqliteStore`; the wiki guide `Extension-types`, "Holding a type in a store"): a binding at the SQL layer would serve every SQL store, one at the SQLite layer only SQLite · OQ59 (the typed store as the one built escape hatch) · Reference §22 "The extension framework" (the architecture's three parts; `stores/sqlite` as "the framework role") · `evaluation.md` (the universal transaction U1–U5 a store honours) · `compiler/src/main/kotlin/velle/Hydration.kt` (`StateResolver`, `CommitCallback`, `Row`, `CommitSet`, `StoreKey`, `CaptureSchema`), `Query.kt` (`QF`, the compiled pre-filter), `StoreGen.kt` (the generated typed store), `stores/sqlite/src/main/kotlin/velle/sqlite/SqliteStore.kt`.

---

## 1. What exists

- **The agnostic layer already exists in substance.** `StateResolver` (fetch by key, scan, join read, filtered scan over a `QF`, capture read) and `CommitCallback.onCommit(CommitSet)` are SQL-free; `Row`, `StoreKey`, `Ref.Persisted`, `CommitSet` with its creations, assignments, captures, retractions, and deletions, `CaptureSchema`, and `QF` are the objects. The universal transaction (`evaluation.md` U1–U5) is stated against them. What it lacks is a name as a layer and a statement that it is the whole of what a store must provide.
- **The SQL layer does not exist.** `SqliteStore` renders `QF` to SQL (`render`, `renderCmp`, the `LIKE` escape), maps `VType` to column types (`sqlType`), creates tables (`createSchema`, membership tables for `many`, capture tables, the union discriminator column), reads and writes columns (`readColumn`, `writeColumn`), encodes constants for push-down (`encode`, degrading what TEXT cannot order), and keys rows on `INTEGER PRIMARY KEY AUTOINCREMENT`. Nearly all of that is SQL, not SQLite; the dialect is the key strategy, the type names, the `LIKE` case folding, and the connection.
- **The typed store** (`StoreGen`) is generated per spec on top of `StateResolver`: an interface of the spec's own questions, a default implementation over any generic backend, and a resolver bridge. It is agnostic today and should stay so; a SQL-layer typed store (hand-tuned SQL per question) is the escape hatch OQ59 describes.

Dave's stance on stores generally (2026-10-24, while settling OQ65 D5): ideally there is one store implementation, because object-relational mapping is a solved problem; Velle *provides* that store and does not *force* it on a system. "When it comes to custom data types, the engineer is explicitly saying they have a custom data layer that they need to fit velle onto. That means dealing with the store." Set aside with it: a type carrying a *carrier*, one of Velle's builtins it encodes itself to so that every store holds it with no new code; it cannot cover the world's types and turns a word the product owner and engineer share into a mapping exercise.

## 2. The split, as stated

1. **Agnostic store API** (`velle.store`, in `compiler/` or its own module): `StateResolver` and `CommitCallback` as they are, named as the contract; every object they exchange; nothing about tables. A store over a binary protocol, a document database, or memory implements this and only this.
2. **SQL store API** (`stores/sql`, new): Velle's one implementation of the agnostic API over the SQL vocabulary: a schema derived from the model (tables, columns, membership tables, capture tables, discriminators), `QF` rendered to `WHERE`, rows read and written through JDBC, constants bound. What it leaves abstract is the dialect: column type names, key generation, `LIKE` semantics, identifier quoting, which comparisons a column type answers.
3. **`SqliteStore`** implements the dialect of the SQL store API and nothing else. A Postgres store is another dialect, mostly type names.
4. **The store API a system provides is given to the compiler.** The output module says which layer its store implements; the compiler and the generators use it: `StoreGen` can emit the SQL-layer typed store as well as the agnostic one; OQ65's E4 checks extension-type bindings against the right layer, so a `SqlTypeBinding<Money>` (column type and JDBC read/write) serves every SQL dialect and Bob writes it once, while a dialect-level binding is only for that dialect.

## 3. What has to be settled

- **Where the layer is declared.** A Gradle dependency alone (`stores:sql` on the classpath), a line in the output module's generate task, or a value handed to `GeneratedSystem`. The spec never says it (Reference §22: the declaration names no mechanism).
- **The dialect interface.** The minimum `SqliteStore` needs to shrink to: type names per `VType` and per extension-type binding, key strategy, `LIKE` escape and case behaviour, identifier quoting, the set of comparisons each column type answers. Whether schema creation is the SQL layer's (model-driven DDL) or the engineer's (migrations), with the SQL layer checking the schema it finds.
- **Extension-type bindings per layer**: `SqlTypeBinding<T>` at the SQL layer with a dialect-independent column type and JDBC calls (today's `SqliteTypeBinding<T>` is `type`, `columnType`, `bind`, `read`, `answers`); whether a dialect may override one; what E4 checks at which layer.
- **Inline bindings and shipped bindings.** Whether the store Velle provides lets the system's engineer register a type's mapping inline, as a pair of lambdas handed to the store, instead of as a binding library, and whether Velle ships bindings for common types (`Money`, a UUID, a URL) with its store.
- **The typed store per layer.** Whether `StoreGen` emits a SQL-layer variant whose default methods are the SQL layer's rendering, so an engineer's override is a hand-written SQL string for one question (OQ59's escape hatch) with every other question still generated.
- **Transactions.** The universal transaction is stated on the agnostic API; the SQL layer owns the JDBC transaction and the agnostic layer's contract says what a non-SQL store owes instead.
- **The tests.** Every example's `*OverSqliteTest` runs today against `SqliteStore` directly; after the split they run against the SQL layer with the SQLite dialect, and the SQL layer gets its own test over an in-memory SQLite that any second dialect can reuse.
