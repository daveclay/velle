# OQ57 — Reads after OQ51: what the query API loads, promises, and leaves to the store

**Status:** open (2026-10-14) — OQ51 settled the read API (2026-10-12, built 2026-10-13); these are its follow-ons, most of them stated by Dave at the settling
**In plain terms:** the caller composes a query from the spec's vocabulary, names its order, and gets model objects back. Left to decide: which related records a read loads and when; what isolation a read may ask for; whether a shape may declare a default order; what a registered query is good for beyond being checked; whether the order-less plain accessors stay; and what the store must promise about keys.
**See:** Reference §22 (the query API, model objects, references, registered queries) · Reference §5, §10 · `evaluation.md` "A read is a read-only snapshot" · `compiler/src/main/kotlin/velle/Read.kt` (`QueryRegistry`), `Codegen.kt` (`fieldHandle`)

---

- **Loading associated and joined records is the caller's choice** (Dave, 2026-10-12). The first build returns references as typed handles navigated lazily. Later, following GraphQL's lead, a query names the relationships it wants loaded with the root, nested to any depth; the framework loads exactly those, batched per level, and every unnamed reference stays a lazy handle, so the N+1 cost is the caller's choice, not the framework's default.
- **Transaction isolation for reads** (Dave, 2026-10-12). Today a query through the read API is a read-only snapshot and nothing else. Let the read request name the isolation it wants (read-committed, repeatable-read, serializable) and let the store binding map it.
- **A default read order per shape** (Dave, 2026-10-12). Today every query must name its order (Reference §22). Decide whether a shape may declare a default that a query inherits when it names none.
- **A registered query's two remaining effects.** A query registered under a name (`QueryRegistry`) is checked against the spec at the engineer's build; it should also get a named candidate method in the generated typed store the engineer can override with tuned SQL (today it rides the generic pre-filter path), and a generated test per registered query. Both need the registry as an input to `gradle generate`, which today runs before the engineer's code exists.
- **The plain accessors** (`invoices()`, `overdueInvoices()`: lists of handles in the runtime's scan order). They are the degenerate read with no order, the only reads left that promise nothing (Reference §22; 2026-10-13). Decide whether they stay now that the query API exists.
- **The typed builder's reach.** v1 exposes scalar and to-one reference members only (`Codegen.kt`, `fieldHandle` returns nothing for collections). Let it filter on collections (`many` fields and inferred inverses: `is empty`, `exists ... where`) and name a union-typed reference's operand.
- **Ordering by the store key is an advisory, not an error** (Dave, 2026-10-12). A query or a selector naming `id` as an order datum has a defined meaning but one the author probably did not intend, since the key is minted and carries no business order (Reference §5, §10); the cursor's hidden tie-break (Reference §22) is the sanctioned use and raises nothing.
- **A deleted row's key is never reissued.** The store conformance pass found SQLite's plain `INTEGER PRIMARY KEY` reissuing a deleted row's key, so a dangling reference silently became a reference to a stranger; the store uses `AUTOINCREMENT` and `CommitSet.Deletion`'s kdoc in `Hydration.kt` states the obligation. Decide whether it joins `evaluation.md`'s universal-transaction contract. Its sibling, scan order as the query surface's order, closed 2026-10-12: no store obligation, every query names its order.
